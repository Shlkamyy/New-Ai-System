- Templates specify appointment creation, status change, invoice creation, payment creation, or addition of a specific procedure **to an invoice**, a relative time **before/at/after**, an integer offset in minutes/hours/days/months, and a message with cursor-insertable variables.

Database triggers capture only **events occurring after migration** (not the imported history). The application materializes due alerts during authenticated foreground queries. Message content is snapshotted when alerts materialize.
- Alerts include patient, template/trigger name, due time and rendered message, with a validated Egyptian WhatsApp deep link (`wa.me`). Clicking **إرسال عبر واتساب** opens WhatsApp; no actual automated messaging, provider integration, WhatsApp delivery verification or background push is claimed. Staff must separately confirm `تم الإرسال` or dismiss the alert.
- Header bell displays the red count for actionable, active, due alerts, refreshed while the logged-in application is foregrounded. No closed-app/background notification guarantee.
- Templates may be created, edited, enabled or disabled by admins. Re-enabling a template does **not** create notifications for events that happened during its inactive period. Queued notices about subsequently cancelled appointments or voided invoice/payment records are suppressed.
- No export of patient phone numbers to third-party messaging providers occurs until an authorized user explicitly opens the WhatsApp link.

## Invoice-item identity and WhatsApp financial accuracy (25 October 2026, development-only)

### Defect reproduced
Before this round, `editInvoice` unconditionally deleted **every** `invoice_items` row and reinserted every row, including unchanged ones. The existing `AFTER INSERT` WhatsApp procedure trigger therefore created new event IDs and potentially duplicate procedure alerts even for a routine price/date/discount correction. The original `procedure` eligibility SQL also inadvertently allowed an event whose referenced invoice item had been deleted.

### Implemented on the feature branch
- Invoice edits now retain existing line-item UUIDs using the current row IDs carried by the edit form; the backend checks that every submitted ID belongs to that particular invoice and rejects repeats or foreign IDs. Existing lines are updated **in place** only when their values change; removed lines are individually deleted; genuinely new lines are inserted once and returned with their new IDs.
- Old clients without item IDs retain unchanged lines through exact content matching; changed lines sent by such clients cannot reliably be distinguished from replacements, so upgrading the editor to send IDs is important.
- The mobile invoice editor includes a hidden `itemId` beside each editable item and sends the IDs when updating a record. New-invoice entry behavior is unchanged.
- WhatsApp event eligibility now requires that a procedure source item still **exists**, its parent invoice is not voided, and its procedure ID still matches the event's recorded filter. As a result, removed or retargeted procedures cannot remain actionable under an obsolete procedure template.
- For pending/available cards, the alert query uses live `invoice_items` description/quantity/unit price and current `payments.amount` instead of old event payload values. Event payloads and sent/dismissed audit states remain unchanged. No auto-send or delivery verification was added.
